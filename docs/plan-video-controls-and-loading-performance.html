1 · Where we are today (code audit)

Video playback

  • Both viewers already render a native player: src/components/ImageViewer.vue:180 and src/components/LibraryViewer.vue:130 use <video controls preload="metadata"> with the cached thumbnail as poster. So basic controls exist — the problems are around them:
  • Keyboard shortcuts fight the player. The global handler (src/composables/useKeyboardNav.ts:16) only yields when e.target is the <video> element itself — i.e. only after the user has clicked the native controls. In the normal case (arrived via ←/→, video not focused) pressing Space jumps to the next unrated image and the arrow keys navigate away mid-playback. There is no way to play/pause, seek, or change volume from the keyboard.
  • No player state persistence. Volume/mute reset on every clip; no loop, no playback speed, no fullscreen shortcut, no frame stepping — all useful when culling clips.
  • PTP videos block on a silent full download. Over PTP, ensurePtpPreview (src/stores/gallery.ts:534) must download the entire movie before the <video> even gets a src. The UI shows only a spinner with “Downloading from camera…” (ImageViewer.vue:175) — no percentage, no transfer rate, no cancel. A 4 GB clip at typical PTP throughput (~25–35 MB/s) is a 2+ minute blank stare.

Download / import pipeline

  • Every PTP download request re-opens a session and re-waits for the catalog. handleDaemonDownload (src-tauri/swift/ptp_bridge.swift:818) runs openSession → waitForCatalog → download → closeSession per request. waitForCatalog blocks until contentCatalogPercentCompleted == 100 — the gallery store’s own comment (src/stores/gallery.ts:43) notes a full-card catalog takes ~45 s. Since each single-file preview download while culling is its own request, the user can pay that session/catalog tax over and over.
  • PTP progress is per-file only; bytes are never reported. The daemon emits one progress line per completed file; the Rust side forwards bytes_copied: 0, bytes_total: 0 (src-tauri/src/commands/import.rs:321). The import screen already computes rate + ETA from bytes and falls back to an indeterminate bar when they’re zero (src/components/ImportProgress.vue:48,96) — so during a video-heavy PTP import the bar sits indeterminate for minutes. “It’s slow” and “it looks frozen” are compounding here.
  • Busy-wait polling adds fixed latency per operation. downloadFile, openSession, closeSession all spin the run loop in 100 ms slices (ptp_bridge.swift:242,139,181). Average ~50 ms wasted per wait × several waits per file × hundreds of files.
  • Apple Photos import sleeps 2 s per batch of 15 (src-tauri/src/commands/import.rs:441): a 300-file import spends 40 s just in delay 2.
  • Preview cache is thrown away at import time. Files already downloaded to ~/.cache/fuji-culler/ptp-preview during culling (potentially including that huge video you just watched) are downloaded from the camera again by the import. The cache is also never pruned.
  • Mass-storage copy is fine. The 8 MB chunked copy with throttled progress (import.rs:14–20) is close to USB-reader line speed; not a bottleneck.

2 · Why the video download “took forever”

For one PTP video, the wall-clock today is roughly:

open session (~1–3 s)
+ wait for catalog (up to ~45 s on a full card — even if it already completed once)
+ transfer (file size ÷ ~25–35 MB/s PTP throughput)
+ close session (~0.5–1 s)
… with zero visible progress the whole time.

The transfer itself is bounded by the camera’s PTP implementation — we can’t make the wire faster. But the session + catalog overhead is pure waste we can eliminate (Phase 1), and the perceived slowness is largely the missing progress feedback (Phase 2). For truly huge offloads, the honest answer is also to steer the user toward mass-storage/card-reader mode (Phase 4).

3 · Phase 1 — PTP session & catalog reuse P0biggest win

All changes in src-tauri/swift/ptp_bridge.swift; no Rust/TS API changes required.

1.1 Keep the session open across daemon requests

  • Add per-camera session state to the daemon (sessionOpen: Bool keyed alongside daemonCameras). handleDaemonDownload / handleDaemonCatalog / handleDaemonDelete call a new ensureSession(camera) instead of unconditionally openSession, and stop closing the session at the end of each request.
  • Close the session only when: the camera is removed (deviceBrowser(_:didRemove:)), the daemon shuts down, or an idle timer fires (e.g. 60 s with no requests — keeps the camera from being locked forever and lets it sleep).
  • Keep the existing “wait for close before replying” behavior when a delete follows an import — ensureSession after an explicit close already handles the reconnect.

1.2 Cache catalog readiness per session

  • Track catalogReady per camera, set by deviceDidBecomeReady(withCompleteContentCatalog:) / the polling fallback, cleared on session close or camera removal. waitForCatalog returns immediately when already ready.
  • Result: the first interaction after connect pays the catalog wait once; every preview and import download after that starts transferring immediately.

1.3 Replace polling waits with callback-driven wakeups

  • In the delegate callbacks (didDownloadFile, didOpenSession…, didCloseSession…), call CFRunLoopStop(CFRunLoopGetMain()) so the RunLoop.main.run(until:) waits return the moment the event lands, instead of on the next 100 ms tick. Keep the deadline loop as a timeout backstop.
Expected impact: single-file preview/video downloads go from seconds-to-minutes of overhead + transfer to transfer time only after the first request. This is the fix for “it just took forever to download the video.”

4 · Phase 2 — Real download progress: bytes, rate, ETA, cancel P0

2.1 Byte-level progress from the Swift bridge

  • Implement the optional ICCameraDeviceDownloadDelegate method didReceiveDownloadProgress(for:downloadedBytes:maxBytes:) and forward it into the existing NDJSON progress stream, throttled to ~100 ms: 
    {"id":7,"event":"progress","completed":3,"total":24,
 "name":"DSCF0042.MOV","bytes_done":812646400,"bytes_file":4294967296}
  • Compute cumulative totals on the Rust side: extend PtpDownloadProgress (src-tauri/src/camera/ptp.rs:68) with optional byte fields; in ptp_import_files_blocking pre-sum bytes_total from the selections (sizes are already in the catalog / ImagePair.hif_size) and fill bytes_copied in the forwarded ImportProgress.
  • No UI work needed for the import screen — ImportProgress.vue already renders bytes, rate and ETA the moment the numbers are non-zero.

2.2 Progress + cancel for in-viewer PTP downloads

  • Route ptp_download_file (src-tauri/src/commands/camera.rs:471) through download_with_progress and add a Tauri Channel parameter so the viewer can subscribe.
  • Replace the bare spinner in ImageViewer.vue:175 with a small progress card: percentage, downloaded/total MB, transfer rate, and a Cancel button. Cancel via a new daemon cancel command that calls ICCameraDevice.cancelDownload(), plus navigation-away cancels the in-flight request for the old file.
  • Keep the existing dedup in ensurePtpPreview; store per-image progress in a small reactive map in the gallery store.

5 · Phase 3 — Video player controls P1

3.1 New shared VideoPlayer.vue component

Extract the two near-identical <video> blocks (camera ImageViewer.vue, library LibraryViewer.vue) into one component with custom controls styled to the existing darkroom UI (same tokens: --color-surface, --color-accent, backdrop-blur bar like .nav-btn):

  • Play/pause button + click-on-video toggles + center flash icon on toggle.
  • Seek bar with buffered-ranges shading, time elapsed / duration (tabular-nums), hover time tooltip.
  • Volume slider + mute, persisted to localStorage so every clip doesn’t reset to 100%.
  • Playback rate menu (0.5× / 1× / 1.5× / 2×), loop toggle, fullscreen button.
  • Auto-hide controls after ~2 s of no pointer movement during playback (like the nav arrows’ hover behavior).
  • Keep the native controls attribute as a fallback prop in case of regressions; poster/thumbnail behavior unchanged.

3.2 Video-aware keyboard map

  • Update the hint bar in the viewer footer to show the video key hints when a video is displayed.

6 · Phase 4 — Smaller performance wins P1

4.1 Reuse the preview cache at import time

  • In ptp_import_files_blocking: before downloading, check ~/.cache/fuji-culler/ptp-preview for each file; if present with the expected size, copy locally instead of re-downloading from the camera. A video watched during culling then imports at disk speed.

4.2 Prune the PTP preview cache

  • LRU cap (e.g. 2 GB, configurable) enforced on app start and after each download — right now watched videos accumulate in the cache forever.

4.3 Trim the Apple Photos import delay

  • Drop delay 2 to delay 0.5 for batches after the first (Photos is already activated), or activate once up front and remove the per-batch delay entirely. Saves ~2 s × (batches − 1).

4.4 Be honest about PTP limits for big video offloads

  • Log measured MB/s per file (bridge stderr already funnels into the app log) so we can tell protocol overhead from wire speed.
  • When an import selection contains > N GB of video over PTP, show a one-line hint with the ETA and a note that a card reader (mass-storage mode) is several times faster. Cheap, prevents the worst experience.

7 · Phase 5 — Stretch goals P2

  • Play-while-downloading for PTP videos. Stream via requestReadDataOfFile(_:atOffset:length:…) into the cache file and start playback once enough is buffered. Caveat: only works when the moov atom is at the front of the file; Fuji MOVs typically put it at the end, so probe first and fall back to download-then-play. Only worth it after Phases 1–2 prove insufficient.
  • Hover-scrub video thumbnails in the grid (generate a sprite strip during thumbnailing).
  • Audio level meter / waveform strip under the seek bar for quickly spotting dead takes.

9 · Risks & open questions

  • Long-lived PTP sessions: some Fuji bodies may drop or misbehave on idle sessions (battery/sleep). Mitigated by the idle-close timer and the existing respawn/reconnect path; needs testing on the actual camera model(s) in use.
  • Delete-after-import ordering: today the close-before-reply dance protects deletes on “some Fuji bodies” (ptp_bridge.swift:171). With persistent sessions, verify delete still works with the session held open — if not, close/reopen specifically around deletes.
  • didReceiveDownloadProgress granularity varies by device; if the camera reports coarsely, rate/ETA smoothing (EWMA over ~5 s) keeps the numbers stable.
  • Keyboard remap on videos changes muscle memory slightly (Space no longer “next unrated” on a clip). The footer hint bar mitigates; worth a quick self-test before settling the final map.
  • Open question: should videos auto-play on open in the viewer? (Suggested default: yes, muted-off, since the user navigated there deliberately.)
